# antipython

An openCode plugin that blocks in-place file edits — anything performed through
a Python interpreter, through a Node.js interpreter (`node`/`bun`/`deno`), or
through any `sed -i` rewrite.

Registered in `~/.config/opencode/opencode.jsonc`:

```jsonc
"plugins": [ ..., "/home/desu/opencode-antipython" ]
```

## Entrypoint gotcha

OpenCode V2 resolves a plugin directory's entrypoint from the **directory root**
(`<dir>/index.js`). It ignores the `main` field in `package.json`. With
`main: "./dist/index.js"` the plugin was silently skipped — no warning, no error
in `opencode.log`, just absent from `/api/plugin`.

The root `index.js` re-exports `dist/index.js` and is what makes the plugin
load. Do not delete it.

To confirm a plugin actually loaded:

```sh
grep 'msg="loading plugin"' ~/.local/share/opencode/log/opencode.log | tail
```

## What it blocks

The `tool.execute.before` hook inspects the `command` argument of `shell`,
`term_host_exec` and `term_pty_exec`, and throws when a Python or Node
interpreter, or an in-place `sed`, is used as the thing that mutates a file.

Note the tool name: V2 renamed the built-in `bash` tool to `shell`. In V1 this
was `bash: "command"`, and a port that misses the rename silently stops
guarding.

| blocked | allowed |
| --- | --- |
| `python3 -c "open('a','w').write(x)"` | `python3 -c "print(1)"` |
| `python3 - <<'PY' ... os.remove(...) ... PY` | `python3 -m pytest -q` |
| `python3 <<< "open('a','w')"` | `python3 script.py --flag` |
| `printf "open('a','w')" \| python3` | `uv run pytest` |
| `cat > fix.py <<'PY' ... shutil.rmtree(...) ... PY` then `python3 fix.py` | `python3 -c "print(len(open('f').read()))"` |
| `python3 -c "import subprocess; subprocess.run(['sed','-i',...])"` | `python3 -c "import sys; sys.stdout.write('x')"` |
| `node -e "require('fs').writeFileSync('a.txt','x')"` | `node script.js --dry-run` |
| `node -e "fs['writeFileSync']('a.txt','x')"` | `node -e "console.log(process.version)"` |
| `node <<'JS' ... fs.rmSync('build',{recursive:true}) ... JS` | `node -p "1+1"` |
| `printf "fs.writeFileSync('a','x')" \| node` | `bun test`, `bun run build`, `deno run -A s.ts` |
| `cat > fix.js <<'JS' ... fs.rmSync('tmp') ... JS` then `node fix.js` | `node -r ./hook.js build.js` |
| `node -e "execSync('rm -rf build')"` | `node -e "console.log(fs.readFileSync('a.txt').length)"` |
| `bun -e "fs.writeFileSync('a.txt','x')"` | `bun x prettier --check .` |
| `sudo -u deploy node -e "fs.writeFileSync('/srv/x','y')"` | `npx tsc --noEmit` |
| `sed -i 's/a/b/' src/app.ts` | `sed -n '1,20p' src/app.ts` |
| `sed -i.bak -E 's/a/b/g' *.ts` | `sed 's/a/b/' f \| diff - f` |
| `find . -name '*.tmp' -exec sed -i '' 's/a/b/' {} +` | `sed -f cleanup.sed f` |
| `for f in *.ts; do sed -i "s/x/y/" "$f"; done` | `sed --help` |

Detection is inline-code only: `python3 script.py`, `node script.js` and
`python3 -m <module>` are always allowed, since a script authored in the repo is
a real script. A script *generated by the same shell command* is treated as
inline code, because that is just an interpreter with extra steps — the same
holds for `.js`/`.mjs`/`.cjs`/`.ts` as for `.py`.

The `sed` rule keys on the in-place flag, not on the substitution script, so a
`sed -i` with any script is rejected. `-i` is recognised in every form GNU sed
accepts — `-i`, clustered (`-ni`, `-Ei`), with a backup suffix (`-i.bak`), and
`--in-place`. `-f script` and `-e expr` consume the rest of their cluster, so
`i` inside them is a filename, not the flag. Flags are matched against the raw
argv token, so a quoted `sed -i` inside an `echo` or a grep pattern is text,
not an invocation. Launchers are followed: `sudo`, `xargs`, and `find -exec`.

For both runtimes, everything before the interpreter word must be a benign
prefix — a runner (`sudo`, `uv run`, `npm exec --`, `timeout 5`), an env
assignment, a shell control word, or an option with its value. A bare word with
no runner in front of it means the interpreter is somebody else's argument:
`echo python3 -c "open('a','w')" >> notes.md` is text being printed, not an
invocation.

Write-intent signals in inline Python code: `open()` in a writing mode,
`os.open` with `O_WRONLY`/`O_CREAT`/..., `.write()`, `.write_text()`/
`.write_bytes()`, `print(..., file=...)` (but not `file=sys.stdout`),
`sys.stdout = ...`, `json.dump`/`pickle.dump`/`csv.writer`, `os.remove`/
`os.rename`/... , any `shutil.*`, pathlib mutations, and `subprocess`/
`os.system`/`os.popen` whose arguments contain a mutating command (`rm`, `mv`,
`sed -i`, `>` ...).

Write-intent signals in inline Node code: any `writeFile`/`appendFile`/
`writeFileSync`/`appendFileSync`/`createWriteStream` identifier (so `fs[...]`
and aliasing are covered too), `unlink`/`rm`/`rmdir`, `copyFile`/`rename`/`cp`,
`mkdir`/`mkdtemp`, `chmod`/`chown`/`truncate`/`link`/`symlink`/`utimes` and
their `Sync` and destructured forms, `fs.open()` in a writing mode, the `Deno.*`
writers, and `child_process` (`execSync`, `spawn`, ...) whose arguments contain
a mutating command. Read-only node is untouched: `fs.readFileSync`,
`fs.existsSync`, `fs.createReadStream`, `process.stdout.write`.

## Development

```sh
bun test          # 186 detector tests
bun run build     # tsc -> dist/
```

`src/detect.ts` is the detector (shell-aware splitter, interpreter finder,
payload classifier, edit-intent scanners for both runtimes, in-place `sed`
finder). `src/index.ts` is the thin plugin wrapper.

Rebuild before testing a change live: `dist/` is what OpenCode loads, and the
root `index.js` re-exports it.
